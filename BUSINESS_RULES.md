# Бизнес-правила

## 1. Канонические термины
Revenue — признанная выручка от реализации.
Income / cash inflow — фактическое поступление денег, согласно терминологии требований проекта. Это не признанная выручка и не прибыль.
Начисленные доходы — выручка и прочие признанные доходы; для этой группы используется отдельное имя Recognized income, а не Income.
Expense — признанный расход; Cost — стоимость приобретения/создания, которая до реализации может оставаться активом.
Payment — подтверждённое движение денег с направлением. План/поручение не равен факту.
Profit — финансовый результат, не остаток денег.
Receivable — признанное требование оплаты; Payable — признанное денежное обязательство.
Аванс клиента — отдельное обязательство исполнения/возврата, не выручка; аванс поставщику — отдельный актив.
Заказ — план исполнения; реализация — отдельное событие признания. Само создание заказа не создаёт выручку.
Для MVP Dashboard показывает прибыль ДО налога на прибыль. Соответственно расходы карточки исключают этот налог, но включают прочие применимые расходы. Чистая прибыль доступна только после настройки и проверки налогового расчёта.

## 2. Даты и источники
Хранить раздельно дату документа, признания, фактического платежа, срок оплаты и время внесения.
Период P относится к признанию либо движению; остатки считаются на дату D. Пользователь видит основание каждого показателя.
Только проведённые операции влияют на факты; исходная операция после сторно остаётся в источнике вместе с отдельной коррекцией. Начальные остатки вводятся отдельными документами открытия и не создают доход/расход текущего периода.
Корректировки учитываются со знаком; технические закрывающие проводки исключаются из оборотов P&L. Исправление не уничтожает исходную запись.

## 3. Формулы результата
Выручка(P) = кредит минус дебет по счетам выручки за P, без технического закрытия.
Прочие доходы(P) = аналогичный чистый оборот по остальным включённым счетам доходов.
Расходы(P) = дебет минус кредит по включённым счетам расходов за P, без технического закрытия.
Выручка отражается после выполнения условий признания, за вычетом скидок и уменьшающих корректировок; налоговые компоненты классифицируются отдельно по принятой политике.
Валовая прибыль = выручка − себестоимость реализации.
Операционная прибыль = валовая прибыль + прочие операционные доходы − операционные расходы.
Прибыль до налога = выручка + прочие признанные доходы − все признанные расходы, кроме налога на прибыль.
Чистая прибыль = прибыль до налога − признанный расход по налогу на прибыль.
Маржа = соответствующая прибыль / выручка × 100%. При нулевой базе не рассчитывается; отрицательная база требует пояснения.
Результат заказа = признанная выручка заказа − относимые признанные затраты. Прямой результат и результат после распределения косвенных расходов показывать раздельно.
Плановые суммы не смешивать с фактом. Неизвестная себестоимость не равна нулю.

## 4. Денежные потоки и долги
Поступления Income(P) = сумма внешних входящих денежных операций с датой фактического движения в P, с учётом технических исправлений этих операций.
Выплаты(P) = сумма внешних исходящих денежных операций с датой фактического движения в P, с учётом технических исправлений этих операций.
Чистый cash flow(P) = Income(P) − Выплаты(P).
Авансы клиентов, полученные кредиты и взносы собственника входят в поступления; принадлежность к поступлениям не означает признание дохода.
Реальный возврат денег клиенту — выплата на дату возврата. Техническое сторно ошибочно внесённого поступления уменьшает показатель поступлений на дату исправления; оно не изображается как реальная выплата. Для исправления выплаты правило симметрично.
Остаток денег = начальный остаток + cash flow для одной валюты без переоценок. Неденежные изменения оценки, если появятся, раскрываются отдельно.
Внутренние переводы исключаются из общего потока, но видны по отдельному счёту. Комиссия отдельна.
Кредиты и взносы собственника не выручка; возврат тела кредита и изъятие капитала не расход.
Непогашенная сумма на D = признанная сумма + увеличивающие корректировки − уменьшающие корректировки − действующие погашения/зачёты до D.
Поздний платёж не уменьшает долг на более раннюю дату. Не допускается распределение сверх доступной суммы.
Полученные авансы = начальные авансы + новые − зачёты − возвраты. Для выданных аналогично.
Просрочка = непогашенные денежные обязательства, срок которых истёк к D. Сроки могут быть по частям документа.
Ожидаемая доплата по ещё не выполненному заказу не автоматически дебиторская задолженность. Условия безусловного требования определяются договором; сложные contract assets за рамками первой версии.
Не сворачивать автоматически разные договоры и валюты.

## 5. Контрольный пример заказа
Условия: заказ 100 000 сом, аванс 30 000; себестоимость 60 000, дополнительные расходы 10 000; налогов нет. До исполнения нет отдельного безусловного требования оставшихся 70 000. Начальные деньги 100 000. Затраты полностью оплачены при исполнении.

| Состояние (накопительно) | Выручка | Расходы | Прибыль | Поступления | Выплаты | Аванс клиента | Долг клиента | Деньги |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| Заказ создан | 0 | 0 | 0 | 0 | 0 | 0 | 0 | 100000 |
| Получен аванс | 0 | 0 | 0 | 30000 | 0 | 30000 | 0 | 130000 |
| Выполнен, аванс зачтён | 100000 | 70000 | 30000 | 30000 | 70000 | 0 | 70000 | 60000 |
| Получена доплата | 100000 | 70000 | 30000 | 100000 | 70000 | 0 | 0 | 130000 |

После исполнения до доплаты прибыль 30 000, денежный поток −40 000. Это не противоречие.

## 6. Номенклатура и себестоимость
PRODUCT — покупной товар/материал; SERVICE — услуга без собственного складского остатка; MANUFACTURED_PRODUCT — собственное изделие.
Производство под заказ — способ исполнения, не четвёртый тип. Комплект товара с услугой — связанные строки предложения с явным распределением пакетной цены.
BOM описывает материалы; операции труда и дополнительные затраты отдельны. Версии и снимок задания неизменяемы после запуска, отклонения согласуются.
Стоимость партии = приобретение после скидок + относимые затраты приобретения.
Базовый метод для взаимозаменяемых запасов — скользящая средневзвешенная оценка после поступления; для уникальных партий — идентифицированная стоимость. Нельзя менять метод задним числом без отдельной процедуры.
Себестоимость реализации = стоимость реально списанных проданных единиц.
Средняя цена = доступная стоимость / доступное количество; при нулевом количестве не делить, проверить состояние.
План производства = нормативные материалы + нормативный труд + прямые дополнительные + допустимые распределённые производственные затраты.
Стоимость выпуска = НЗП начала + включаемые затраты − НЗП конца − отдельно учтённые выбытия из НЗП.
Стоимость единицы = стоимость соответствующего годного выпуска / количество; частичный выпуск не поглощает всё НЗП.
Распределение = сумма × база объекта / общая база. При нулевой базе блокировка или явно утверждённое правило.
Припуск к потребности: Q × (1+k). Потери как доля входящего материала: Q / (1−w), где 0 ≤ w < 1. Эти правила не равнозначны.
Пригодные остатки возвращаются на склад с распределённой стоимостью; брак и ненормативные потери учитываются отдельно. Резерв и перемещение в цех не равны потреблению.
Отрицательные доступные остатки в MVP блокируются. Поздняя стоимость корректирует оценку контролируемо, не подставляется ноль.

Пример стеклопакета, условный 1×1 м без потерь: стекло 2 м² × 600 = 1200; рамка 4 м × 80 = 320; герметик 0,4 кг × 500 = 200; труд 1 ч × 300 = 300; упаковка 80; производственные расходы 120. Итого 2220 сом.
Две заготовки не означают два целых складских листа. Размеры, единицы и пересчёт проверяются.

## 7. Зарплаты
Условия оплаты версионируются по датам; несколько компонентов допускаются.
Оклад за неполный период определяется выбранным законным правилом; пример по часам: оклад × учитываемые часы / индивидуальная норма.
Часовая = подтверждённые часы × ставка; дневная = оплачиваемые дни × ставка; сдельная = сумма принятых объёмов × расценки.
Комиссия = допустимая база × ставка × доля участия. База, скидки, налоги, возвраты, момент права и дата ставки задаются явно.
Для мастера СТО база работ отделена от запчастей. Комиссия по оплате учитывает только связанную долю частичного платежа.
Начислено = назначенные компоненты + премии/бонусы ± корректировки.
После удержаний = начислено − допустимые удержания.
Осталось выплатить = после удержаний − связанные выплаты − зачтённые авансы, без двойного вычитания.
Затраты работодателя = начисления + применимые взносы за его счёт. Выплата не создаёт второй расход.
Аванс — деньги, а не отрицательное начисление. Переплата не становится автоматически разрешённым удержанием.
Каждая строка имеет версию правила, источник, количество, базу, ставку, округление и подтверждение.
Производственный труд включается в стоимость только один раз. Нормативная оценка заменяется/корректируется фактом, не суммируется с ним.
Удержания требуют основания и проверки местных ограничений. Произвольных «штрафов» нет.

Примеры до удержаний:
- продавец: 30000 + 3% × 400000 = 42000;
- швея: 120 × 250 = 30000;
- мастер: 40% × 150000 стоимости работ = 60000;
- менеджер за полный период: 40000;
- рабочий: 1800 × 22 = 39600.
Пример листка: 30000 оклад + 12400 комиссия + 3000 бонус = 45400 начислено; удержаний нет в примере; аванс 10000; остаток 35400.

## 8. Dashboard: источники
Все карточки используют один согласованный снимок/версию и общие фильтры tenant/организации/валюты.
P — полуоткрытый интервал [начало, конец) в часовом поясе бизнеса. Начисления отбираются по recognition_date, деньги — по payment_date. Для остатков D означает конец выбранного дня; будущие события не включаются.
В формулах ниже R(o,D) — непогашенная сумма конкретного обязательства из раздела 4. Авансы и неразнесённые оплаты показываются отдельно; долги разных документов не сворачиваются автоматически.

| Карточка | Формула | Источник |
|---|---|---|
| Выручка за P | Σ(credit − debit) по счетам выручки за P, без технического закрытия | journal_entries, journal_lines, ledger_accounts; recognized_income_entries, sales |
| Прибыль до налога за P | Выручка + прочие признанные доходы − расходы до налога на прибыль | Журнал, recognized_income_entries, expense_entries |
| Расходы за P | Σ(debit − credit) по счетам расходов за P, исключая налог на прибыль и техническое закрытие | journal_entries, journal_lines, expense_entries, financial_categories |
| Деньги на D | Σ(debit − credit) всех проведённых строк денежных счетов до D включительно, с документами начальных остатков | accounts, ledger_accounts, journal_entries, journal_lines; детализация cash_transactions и документы открытия |
| Клиенты должны на D | Σ R(o,D) по денежным требованиям к клиентам | obligations, settlement_allocations, journal_entries, customers |
| Мы должны поставщикам на D | Σ R(o,D) по денежным обязательствам перед поставщиками | obligations, settlement_allocations, journal_entries, suppliers |
| Зарплаты к выплате на D | Σ R(o,D) по зарплатным обязательствам после удержаний, связанных выплат и зачтённых авансов | salary_statements, salary_entries, obligations, settlement_allocations, journal_entries |
| Активные заказы на D | COUNT DISTINCT подтверждённых/в работе/частично выполненных/готовых к передаче | orders, document_status_events |

Полностью выполненный неоплаченный заказ — долг, а не активный заказ.
График «Начисленные доходы и расходы»: доходы = выручка + прочие признанные доходы, расходы = состав карточки расходов; обе серии по дате признания. График прибыли использует формулу карточки прибыли до налога.
График «Движение денег»: отдельно Income/поступления, выплаты и их разница по датам денежных операций. Поступления не подставляются вместо выручки. Внутренние переводы между счетами бизнеса исключены из общего потока.
Категории расходов взаимно исключаются; сумма категорий и сумма временных интервалов равны соответствующей карточке при тех же фильтрах.
Исторические состояния не вычисляются по текущему status.
Детализация 450000 расходов может состоять из 280000 себестоимости + 90000 административной зарплаты + 40000 аренды + 25000 рекламы + 15000 прочих. Производственная зарплата внутри себестоимости повторно не прибавляется.
Низкий склад: годный доступный остаток − резервы < заданного минимума по SKU/складу. Порог хранится в inventory_reorder_rules; будущая поставка не фактический остаток.
Ноль, отсутствие данных, отсутствие прав и ошибка различаются. История ввода не гарантирует полноту реального учёта.

### Раскрытие каждой суммы
Карточка → показатель с периодом/датой, валютой, фильтрами и версией формулы → строки вклада → исходный документ и его журнал либо денежное движение. Сумма всех строк вклада равна итогу; итог страницы при пагинации подписывается отдельно.
Строка содержит источник и его ID, дату, категорию, точную сумму со знаком и объяснение включения. Для долга показываются начисление, корректировки, зачёты и остаток; для прибыли — доходы с плюсом и расходы с минусом; для денег — начальные остатки и движения.
Фильтры и права проверяются сервером и при открытии источника. При обновлении данных карточка и детали получают новый согласованный снимок с отметкой времени; сумма из старого снимка не выдаётся за сумму новых строк.
Неполный учёт и неподтверждённая себестоимость отмечаются рядом с итогом. Нельзя заявлять полную прибыль только потому, что арифметически сошлись введённые операции.

## 9. Прогноз
Прогнозный остаток(t) = доступные деньги сейчас + сценарные поступления до t − плановые выплаты до t.
Дополнительная трата сегодня = max(0, min по горизонту [остаток(t) − резерв(t)]).
Отрицательная величина отдельно показывается как кассовый разрыв с датой. Связанные планы/обязательства не вычитаются дважды.
Указываются горизонт, сценарий, ограничения денег, неопределённые поступления, недостающие расходы. Это оценка, не гарантия.

## 10. Инварианты приёмки
Дебет = кредит; детализация = итог; allocations ≤ источник; распределённые затраты = источник после завершения; повтор запроса не дублирует событие; аванс/кредит не выручка; выплата не повторный расход; роли/tenant соблюдены; закрытые периоды защищены.
Контрольные примеры являются основанием будущих автоматических тестов, а не отчётом об уже запущенных тестах.

## 11. Money Policy MVP (ADR-031)
Одна base currency на Business; все его счета, документы, обязательства и проводки в этой валюте. Валюта выбирается при создании бизнеса из проверенного справочника, не выводится из языка браузера. После первого проведения её изменение в MVP запрещено. FX и пересчёт валют вне MVP.

| Значение | PostgreSQL | Обмен DB → backend → frontend |
|---|---|---|
| Итоги, платежи, проводки, погашения | NUMERIC(20,4) | Строка с 4 знаками после точки + currency |
| Цена / стоимость единицы | NUMERIC(24,8) | Строка с 8 знаками |
| Количество, часы, размеры | NUMERIC(20,6) | Строка с 6 знаками |
| Доля единицы | NUMERIC(12,8) | Строка с 8 знаками; диапазон задаётся правилом |
| Курс (зарезервирован для будущего FX) | NUMERIC(24,12) | В MVP не используется для пересчёта |

Максимальный модуль суммы — 9999999999999999.9999; итог после округления тоже проверяется на переполнение. Справочник валют MVP поддерживает minor_units от 0 до 4; значение фиксируется при начале учёта. Точность хранения не разрешает оплату долями меньше денежной единицы валюты.
API Money: {"amount":"123.4500","currency":"KGS"}. Код KGS здесь пример, не выбор валюты бизнеса. Денежный ввод API — только десятичная строка без экспоненты, пробелов, группировки, NaN/Infinity; превышение допустимого scale отклоняется, а не молча округляется. Локализованный ввод UI преобразуется в каноническую строку и повторно валидируется сервером. Отрицательные суммы разрешены лишь в контрактах корректировок/отчётов; обычный payment положителен, направление отдельно.

Decimal.js: отдельный контекст с precision=64 значащих цифры, rounding=ROUND_HALF_UP (при точной половине — от нуля). Создавать Decimal только из строки; не использовать Number, parseFloat или арифметику JS number для денег, цен, долей и количеств, влияющих на деньги. Настройки контекста не изменять глобально в разных модулях.
Цена × количество, скидка и распределяемая база считаются с рабочей точностью. Округление до minor_units выполняется при фиксации денежного итога строки, начисления, платежа или доли распределения. Итог документа — сумма уже зафиксированных строк; повторное округление независимого общего произведения не меняет итог. Отчёты суммируют записанные значения. При сохранении цена округляется явно до 8 знаков, затем служит снимком для расчёта строки; количества не округляются скрыто.
Перед INSERT значение уже приведено к целевому scale и диапазону. Автоматическое округление NUMERIC при записи не является бизнес-правилом. Налоговая/зарплатная локализация может потребовать иной режим: только версионированным решением до автоматизации, без изменения прошлых документов.

Распределение общей суммы: округлить источник до minor_units, вычислить точные доли по неотрицательной базе, усечь модули долей до minor_units и раздать оставшиеся минимальные единицы по убыванию дробного остатка; при равенстве — по стабильному ID строки. Для отрицательного источника распределить модуль и вернуть знак. При нулевой общей базе операция блокируется. Сумма долей строго равна источнику; остаток не теряется и не превращается в произвольный расход.
Контрольные примеры при minor_units=2: 0.10 + 0.20 = 0.30; 1.005 → 1.01; −1.005 → −1.01; 100.00 на три равные доли → 33.34 / 33.33 / 33.33. Сторно использует противоположные исходные записанные суммы, а не перерасчёт по новой цене.
Frontend форматирует строки для показа; Money остаётся точным в формах, детализации и экспорте. Исключение для чисел — нормализованные координаты графика по ARCHITECTURE.md.

## 12. Даты, календарь и период учёта (ADR-032)
Business.timezone — явно выбранный IANA timezone, например Asia/Bishkek; сервер валидирует его. В MVP timezone фиксируется после первого проведения, чтобы не менять историческую группировку денег. До проведения смена настройки аудируется. Browser timezone — удобство ввода, не источник истины.

| API / понятие | Поле БД | Семантика |
|---|---|---|
| createdAt / updatedAt | created_at / updated_at, timestamptz | Момент создания/последней разрешённой правки; задаёт сервер/БД, передача RFC 3339 в UTC с Z |
| documentDate | document_date, date | Дата исходного документа, может отличаться от признания |
| transactionDate | recognition_date, date | Хозяйственная дата признания; определяет P&L и accounting period |
| paymentDate | payment_date, date | День фактического движения в timezone бизнеса, определяет денежный отчёт |
| occurredAt / paidAt | occurred_at / paid_at, timestamptz, nullable | Точный момент движения, если известен; не выдумывать полночь при наличии только даты |
| dueDate | due_date, date | Последний день своевременной оплаты; просрочено, если due_date < дата среза и остаток > 0 |
| accounting period | start_date / end_date, date | Полуоткрытый интервал [start_date, end_date), месячный период организации |

Если известен точный момент платежа, paymentDate вычисляется в timezone бизнеса; переданное несовпадающее значение отклоняется. При ручном вводе только даты сохраняется paymentDate, точное время остаётся NULL. Документ payment и его cash_transactions имеют согласованную дату; createdAt никогда не заменяет её. Начисление и платёж могут относиться к разным периодам.
«Сегодня» — дата серверных часов в timezone бизнеса; неделя — понедельник 00:00 до следующего понедельника; месяц — первое число до первого следующего месяца; год — 1 января до 1 января следующего года. Настраиваемый финансовый год показывается отдельно с явной подписью, календарный год не переопределяет.
Для date фильтры сравнивают даты; для timestamptz границы вычисляются в timezone и затем переводятся в UTC. При DST сутки не предполагаются равными 24 часам; несуществующее/неоднозначное введённое локальное время требует уточнения offset, не молчаливого сдвига.
Срез «на D» включает события по дату D включительно; текущий день — только уже проведённые факты. Будущая дата фактического платежа/признания в MVP запрещена, будущие намерения — планы. Дата ввода и дата действия истории различаются.
Периоды организации не пересекаются. Начальные остатки вводятся на дату старта учёта отдельным документом. Проведение, изменение погашения и сторно блокируют строку периода и проверяют OPEN; закрытие периода использует ту же блокировку. В CLOSED проводить нельзя. Исправление прошлого — в текущем открытом периоде либо после явного periods.reopen с причиной и аудитом. Повторное открытие не удаляет ранее выданные отчёты; новая версия показывает обновлённые данные.

## 13. Жизненный цикл финансовой истории (ADR-033)
Общего enum для всех сущностей нет; документ имеет тип и разрешённые для этого типа переходы. Права, версия, период и основания проверяются перед переходом.

| Сущность | Состояния и допустимые переходы |
|---|---|
| Финансовый документ, реализация, payment, поступление | DRAFT → POSTED либо VOID; POSTED неизменяем, VOID терминален |
| journal_entry | DRAFT → POSTED в одной transaction с документом; проведённые строки не меняются |
| Заказ | DRAFT → CONFIRMED → IN_PROGRESS → PARTIALLY_FULFILLED → FULFILLED; READY допустим перед FULFILLED; CANCELLED только для неисполненного остатка |
| salary_run | DRAFT → CALCULATED → APPROVED → POSTED; CALCULATED → DRAFT при пересчёте, APPROVED → DRAFT при отзыве утверждения; CANCELLED только до POSTED |
| accounting_period | OPEN → CLOSED; CLOSED → OPEN только с periods.reopen, причиной и аудитом |

Переходы исполнения могут пропускать промежуточное состояние, если подтверждены все необходимые события; нельзя откатить исполненную часть заказа в черновик. При частичной отмене история исполненной части сохраняется.
REVERSED — вычисляемое состояние полного технического сторно исходного документа; PARTIALLY_REVERSED — частичного. REFUNDED/PARTIALLY_REFUNDED — вычисляемое состояние реального возврата денег. Они не заменяют POSTED в журнале и не исключают исходную запись из отчётов.
Сторно — новый проведённый документ, связанные обратные проводки и корректирующие allocations/движения со своей датой. Старый период сохраняет исходную операцию; новый отражает коррекцию. Реальный возврат — отдельный payment с refund_of_payment_id; возврат товара/уменьшение реализации — отдельное основание. Один возврат денег сам по себе не отменяет выручку.
Суммарное сторно/возврат ограничено доступной суммой исходника под блокировкой; возврат и техническое исправление имеют разные основания и проверку согласованности. Повтор запроса защищает idempotency key.
В MVP финансовые документы, включая VOID и черновики с историей, физически не удаляются. Архивирование справочника не удаляет ссылки. Техническое удаление тестовых данных возможно только в изолированном окружении по правилам безопасности.

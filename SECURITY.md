# Безопасность

## Модель доступа
Права принадлежат членству пользователя в конкретном бизнесе, не глобальному users.role.
Решение: активная сессия + активное членство + разрешение + область + принадлежность объекта + допустимое состояние.
По умолчанию отказ. Проверка в каждом application service; frontend лишь скрывает ненужные элементы.

## Роли
OWNER: все полномочия своего бизнеса; не обход целостности, аудита и подтверждений.
ADMIN: обычные настройки, операционные разделы, делегированное управление участниками; финансовые/зарплатные сведения не выдаются автоматически.
ACCOUNTANT: финансовый учёт, взаиморасчёты, зарплаты и разрешённые отчёты; перевод владения не разрешён.
MANAGER: клиенты, заказы, склад и производство в назначенной области; зарплаты закрыты.
EMPLOYEE: свои задания, выработка и свой листок; не вправе утверждать собственные исходные данные без отдельной политики.
VIEWER: явно разрешённые отчёты/показатели; без мутаций.
Роли — стартовые шаблоны; проверяются конкретные grants.

## Области и делегирование
BUSINESS, ORGANIZATION, DEPARTMENT, ASSIGNED, SELF, EXPLICIT. Допустимые области зависят от permission.
Объединяются целые пары действие+область. «Читать все» и «менять свои» не дают «менять все».
Нет произвольных per-user allow/deny в MVP. Отдельные field projections скрывают зарплаты, реквизиты и себестоимость.
reports.read не открывает все отчёты; агрегаты, детализация и экспорт настраиваются отдельно.
ADMIN назначает только делегированный набор и не повышает себя до OWNER. Нельзя удалить последнего владельца.
Передача владения требует специального подтверждения и усиленной аутентификации. Изменение роли инвалидирует кэш полномочий; долгоживущий токен не является единственным источником прав.
При принятии приглашения и исполнении фонового действия проверяются текущие права.

## Tenant isolation
business_id NOT NULL, составные FK, RLS с проверкой чтения и новых строк, FORCE RLS. Runtime не owner/superuser/BYPASSRLS.
Контекст устанавливает backend после проверки членства, локально в транзакции. Клиентский businessId — входной параметр, не полномочие.
RLS не заменяет ограничения полей/отчётов и application authorization.
Views, кэши, files, AI, exports и queue не обходят tenant. Auth-глобальные таблицы имеют отдельные ограниченные права.
Проверять connection-pool reuse, прямую подмену UUID и межtenant FK.

## API и validation
Server Actions считаются публичными точками входа. HTTPS; проверенные сессии, secure/httpOnly cookies и применимая CSRF-защита; ограниченный CORS не заменяет auth.
Zod: структура, форматы, размер, диапазоны, decimal-строки, допустимые поля. Запрет mass assignment: actor, approved_by, posted и рассчитанные итоги задаёт сервер.
Параметризованный SQL. Проверка всех связанных объектов, статусов и версий.
Транзакции, идемпотентность, блокировки при погашениях/остатках. При тайм-ауте сначала получить статус исходной команды.
Ошибки без SQL/стеков/секретов и раскрытия существования чужого объекта.

## Rate limiting
Общие для экземпляров счётчики по пользователю, бизнесу, действию и где уместно IP:
- login/MFA/reset и отправка писем;
- приглашения и изменения прав;
- финансовые команды и подтверждения;
- AI: запросы, время, tool calls, бюджет;
- отчёты/экспорт/импорт: объём, диапазон, параллелизм;
- upload/download: размер и частота.
Численные лимиты определяются нагрузочными тестами. 429 с временем повтора. Прогрессивная защита входа не должна позволять легко заблокировать чужой аккаунт.

## Аудит и данные
audit_logs: tenant, actor, действие, объект, время, request ID, результат, допустимые изменения, источник, ссылки на подтверждение.
Бизнес-изменение и аудит атомарны; отказы пишутся в security_events вне откатившейся транзакции.
Журнал недоступен для обычного изменения/удаления, включая OWNER. Инфраструктурный администратор — отдельная граница доверия; неизменяемость от него не обещается.
Не хранить пароли, токены, полные реквизиты/документы в технических логах. Зарплатный аудит защищён зарплатными правами.
Секреты в менеджере секретов, ротация, минимальные IAM-права. Приватный S3, временные ссылки, карантин файлов. Backup/PITR и проверка восстановления до production.
Сроки хранения и размещение данных — открытые решения до production.

## Подтверждения
AI не исполняет финансовые команды. Proposal → проверка → карточка → подтверждение → повторная проверка → идемпотентное исполнение.
Подтверждение не выдаёт недостающие права. Смена параметров/версии аннулирует его.
MFA требуется проектной политикой для привилегированных ролей; усиленная проверка для владения/доступов и будущих банковских операций.

## Приёмочные проверки
Подмена tenant/UUID; запрещённые поля; чужой листок; утечка через отчёт/экспорт/AI/аудит; self-escalation; отзыв роли при открытой сессии; повтор подтверждения; гонки платежей; устаревший объект; prompt injection; повторное использование соединения другим tenant.
Тестировать runtime-ролью, а не владельцем таблиц.

## Bootstrap и текущий доступ (ADR-034)
Сервер получает user.id из проверенной Better Auth session. Клиентские userId, businessId, role и permissions не определяют полномочия; businessId — только запрошенный бизнес.
До установки tenant-контекста сервер вызывает узкую служебную операцию list_my_memberships для этого user.id. Она возвращает только его активные членства и минимум сведений о бизнесах. Общий SELECT всех memberships через публичный API запрещён.
Механизм БД: ограниченные SECURITY DEFINER функции для поиска собственных членств и создания бизнеса, фиксированный search_path, schema-qualified объекты, без dynamic SQL; EXECUTE отозван у PUBLIC. Владелец функций — отдельная NOLOGIN-роль с только нужными правами/политиками, не superuser, не BYPASSRLS и не мигратор. Никакой универсальной функции выполнения SQL. Аргумент user.id задаёт доверенный backend после проверки сессии; прямого доступа клиентов/LLM к соединению нет.
create_business создаёт новый UUID бизнеса, единственную организацию, membership OWNER, системные роли/grants и audit атомарно. Она не присоединяет пользователя к произвольному существующему businessId. Принятие приглашения — другой узкий сценарий с одноразовым токеном, проверкой email, срока, пригласившего и актуальных прав.

После bootstrap — transaction на одном соединении: локальный контекст user/business → повторная проверка активных user/business/membership и текущих grants → scope/владелец объекта → действие. Отсутствующий/ошибочный контекст означает отказ. По завершении transaction контекст не сохраняется в pool.
Для мутаций membership/authorization_version и строки затрагиваемых grants защищаются согласованными блокировками с операциями отзыва прав; изменение, начавшееся после отзыва, не использует старый кэш. Уже начатые операции и отзыв сериализуются, граница фиксируется в integration tests. Простая cookie с ролью не служит источником permissions.
Runtime-роли auth, application, worker и migrator раздельны. Auth-роль ограничена auth-таблицами и узкими служебными функциями; application не читает credentials; worker не получает DDL; migrator не используется в web. RLS защищает от ошибочных запросов, но не обещает защиты от полностью скомпрометированного backend, способного устанавливать доверенный контекст.

## Audit Log: контракт до/после (ADR-035)
Каждая запись: id, business_id, actor_member_id либо system_actor (ровно один действующий тип исполнителя), action, entity_type, entity_id, previous_value, new_value, occurred_at (серверный UTC), request_id, result, metadata и schema_version.
previous_value/new_value — серверные снимки разрешённых полей, а не произвольный request body. Создание: previous_value=NULL; правка: обе проекции; переход статуса: старый/новый статус и версия. Для сторно/возврата сохраняются исходный ID, новый ID, сумма/валюта, дата и причина. Decimal в JSON — строка.
Allowlist по типу события: финансовые суммы/статус/основания; зарплатные ставки/начисления только в защищённой зарплатной проекции; роли — role IDs, grants и scopes до/после; настройки — только изменённые разрешённые ключи. Пароли, session/API tokens, MFA secrets, банковские credentials и полные документы не сохраняются. Redaction обозначается явно, не подменяет значение пустой строкой. metadata ограничена request/job ID, источником UI/AI/worker, reason, proposal/approval ID, версией расчёта; никаких полных prompts или секретных headers.
Финансы, зарплаты, платежи, возвраты, отмены, роли, permissions, настройки, смена валюты/timezone до начала учёта и будущие AI writes обязательно аудируются. Неудача вставки audit отменяет предметную мутацию.
Изменение payment + allocations/остатки обязательств + journal + audit + idempotency result + необходимый outbox — одна DB transaction. Долг вычисляется по obligations/allocations, отдельный редактируемый баланс не нужен. Любая ошибка откатывает все эти изменения; security-событие отказа записывается после rollback отдельно и безопасно.
Аудит append-only: приложение и OWNER не могут UPDATE/DELETE. Чтение/экспорт требует audit.read/export и права на чувствительную предметную область (например salary.read); системная роль OWNER также проходит server policy. Публичный API не получает full before/after без field projection. Срок хранения определяется до реальных данных/production.

## Общие ограничения сервисов
Rate limiting для нескольких экземпляров хранится в PostgreSQL: Better Auth database storage для auth; атомарные tenant_rate_limits для прикладных действий. In-memory счётчик не единственная защита. При недоступной защите login, изменения прав и AI-команды завершаются безопасной временной ошибкой.
Стартовые dev/test лимиты фиксируются в P01.1/P14.1; до открытия staging для внешних пользователей требуются явные значения, до production — измеренная настройка. Не оставлять endpoint без лимита до PHASE 15.
Ошибки сервиса возвращают стабильный code, безопасное сообщение, fieldErrors при валидации и requestId; техническая причина доступна только в отредактированном server log. Чужой объект не раскрывается через различие ошибок; повтор платежа после timeout сначала сверяется по idempotency key. Пустой catch запрещён.

## Публичные аккаунты раннего доступа (ADR-042)
SITE-01 допускает только profile identity и auth lifecycle. Auth: Better Auth/D1, пароль 12–128 символов и hash; Secure/HttpOnly/SameSite cookie на HTTPS, session expiry 7 дней. Origin точного SITE_URL проверяется для всех POST, signup требует текущую legal version, body ≤8192 bytes. Допустимые endpoints перечислены на сервере; дополнительные auth routes закрыты.
Кабинет и профиль проверяют серверную сессию. Клиентские user/role/business ID не полномочия; browser response не содержит bearer session tokens. Auth responses/private page no-store; restrictive headers и origin-bound cookies. Лимиты хранятся в D1: signup 5/60s, signin 10/60s, password/delete 5/60s, общие 60/60s; IP берётся только из Cloudflare-controlled header. Auth logger выключен; неожиданная ошибка логирует безопасную категорию.
Email пока не verified; recovery/привилегированные роли/MFA отсутствуют, поэтому реальные финансовые данные, бизнес-модули, документы и финансовые инструменты выключены. Удаление профиля разрешено только владельцу с паролем и отзывает сессии. Включение учёта требует штатных P01 permissions/tenant/MFA/verification и PostgreSQL controls из основного раздела.
